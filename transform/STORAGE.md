# hokhong.tw 儲存結構

2026-09-12 定案。四個決定由你選定：**DuckDB + Parquet**、**append-only + contentHash**、**預先算好 per-page JSON**、**原始檔留在專案目錄**。

> **這份文件不寫現況數字。**
> 列數、交易日數、頁數、磁碟佔用、覆蓋率、有零售實測的品項數、幾支來源、幾步轉換，全都會隨每日
> 資料更新或程式增刪而變，寫進 Markdown 隔天就是錯的，而且錯得很有說服力。要看現況就跑指令，
> 輸出即事實：
>
> ```bash
> node scripts/status.mjs           # 全部
> node scripts/status.mjs steps     # 取得層幾支（各支 id 與頻次）、轉換層幾步與步名順序
> node scripts/status.mjs data      # 各層列數、對帳六列、覆蓋率、聚合四表、磁碟佔用、parquet 檔數
> node scripts/status.mjs page      # 頁數與可收錄比例、零售與價格鏈覆蓋、買菜清單、颱風
> node scripts/status.mjs release   # 兩個 release tag 各資產的現值大小
> node scripts/status.mjs online    # 最近幾次 daily.yml、Pages 設定與憑證、線上 sitemap 筆數
> ```
>
> 本文出現的數字只有三類，三者都不會因為今天資料更新而失效：
>
> 1. **設計常數**——門檻、規則、單位、判準（收錄門檻「近 90 天 30 個交易日、交易量 ≥ 10,000 公斤」、
>    價格鏈的「批發 ÷ 產地落在 1.0–4.0」、`cover < 0.35`、分頁數上限 5 之類）。改它要動程式，不是等資料變。
> 2. **標了日期的歷史量測／一次性基準**——DuckDB 選型時的效能基準、踩坑當時的值、版面像素、色彩 ΔE。
>    這些是論證材料，寫的是「當時量到什麼」，每一處都註明日期與重現方式（哪支 `ingest/probe/*.mjs`、
>    或哪個 `data/page/**.json` 欄位）。要重量就跑註明的那一支。
> 3. **外部來源的事實**——政府平台自己公布的東西、別的專案的量級、WCAG 的對比門檻之類。
>
> 本機 checkout 的 `data/` 常常落後線上好幾天（每日更新發生在 Actions 的 runner 上），所以
> `status.mjs data page` 講的是本機；要講「現在站上是什麼」，權威輸出是 `status.mjs online`
> 以及它指出的那次 run 的 `gh run view <id> --log`。

## 1. 為什麼這裡需要 DuckDB，而 seh.tw 不需要

seh.tw 的結論是「全檔案、無資料庫」，那是對的——它 11,361 頁、2,806 個活動。這裡的量級差了三個數量級：

| | seh.tw | hokhong.tw |
|---|---|---|
| 核心資料列 | 約 1.1 萬 | **千萬級**（`status.mjs data` 的「L1 行情」） |
| 原始檔 | 100 MB，每日覆蓋 | 好幾百 MB，逐日累積（`status.mjs release` 的 `history-raw`） |
| 變更歷史 | `git log -p` 就是歷史 | git 放不下逐日 diff，要自己存 |

2026-09-12 量測，當時 14,694,536 筆（Node 22.17、DuckDB 1.5.5、單機）。這一組是選型的依據，不是現況；
要重量跑 `ingest/probe/duck-probe.mjs`：

```
直接掃 373 MB 的 gz JSON 做全史聚合      14.8 秒
轉成 Parquet（zstd）一次性全量            17.7 秒 → 147 MB（單檔 PARTITION_BY）
轉成 Parquet（zstd）一天一檔 5,362 檔     142 秒 → 248 MB（實際採用，見 §4）
Parquet 查詢：單品項 × 單市場 全史 14 年   32 ms
Parquet 查詢：年 × 種類 全史聚合          44 ms
Parquet 查詢：單一作物月加權均價 14 年      45 ms
Parquet 查詢：單日全市場（首頁用）          7 ms
```

**關鍵差距是 14.8 秒 vs 32 毫秒。** 每天 build 要算上千組頁面（當初 README §6 估 6,000 組），每組都掃一次 gz 是不可行的；轉成 Parquet 後每個查詢是毫秒級。這就是引入 DuckDB 的唯一理由——它只是 build 期間的計算工具，**產出仍然是純靜態檔案，線上不需要資料庫**。

### 什麼時候該重新考慮

每年新增約 100 萬筆（33 MB gz / 13 MB Parquet）。以 2026-09-12 量到的速度推估，十年後是 2,500 萬筆、370 MB Parquet，查詢仍在百毫秒內。**這個決定在可見的未來不需要改。**

## 3. observation：append-only 怎麼在千萬列的量級下成立

seh.tw 把整個 payload 存進 NDJSON 再靠 git diff 當歷史。這裡不能照做：千萬列的 NDJSON 每天一次 diff，git 會爆掉。

改成**只存鍵 + 內容雜湊 + 三個時間欄**，實際的價格留在 `data/parquet/`：

```
鍵      (交易日期, 種類代碼, 市場代號, 作物代號)      ← 實測無重複鍵
內容    contentHash = hash(上價,中價,下價,平均價,交易量)
時間    firstObservedAt / lastVerifiedAt / lastChangedAt
```

每日處理（語意與 seh.tw §2 相同，只是換成集合運算）：

```
重抓近 7 天 → 與 current.parquet 依鍵 join
  hash 相同  → 只更新 lastVerifiedAt
  hash 不同  → 舊列寫進 observation/history/，current 更新 hash 與 lastChangedAt   ← 這就是「事後修正」
  鍵不存在   → 新增，firstObservedAt = 今天
  日曆說該有交易卻沒有這個鍵 → 記入健康檢查，不刪除既有列
```

2026-09-12 量測的成本（當時 1,469 萬列；重現：`ingest/probe/duck-hash.mjs`）：

```
對 1,469 萬列算 md5                       16.3 秒（一次性建表）
重抓 7 天（約 1.8 萬列）vs 現值表 找變更      58 ms     ← 每日只付這個
重抓 7 天 找新增列                          53 ms
全量比對 1,469 萬 vs 1,469 萬（最壞情況）    17.4 秒
2026-09-04～09-10 實際變更列                0 筆      ← 與逐檔比對的結果一致
```

**比對本身是 58 毫秒**，因為只比對重抓的 7 天。但 `observe.mjs` 整支跑完是秒級——時間花在把上百 MB 的 current 載入記憶體、合併後整檔重寫（Parquet 無法就地更新）。這是每日的真實成本，仍然遠低於每天重算全史。每日實際耗時與「未變／修正／新增」看 `status.mjs data` 的「observation」那一行（線上的看 run log 的 `observe` 那一行）；current 的檔案大小看同一支的磁碟佔用。全量比對（`--all`）只在懷疑資料錯亂時才跑。

2026-09-12 量測：初始化（`--init`，當時 1,469 萬列算雜湊並寫檔）4.3 秒；每日增量 5.6 秒。

`lastVerifiedAt` 與來源自己的更新時間是兩件事（同 seh.tw §2）。這裡的來源沒有提供任何「資料更新時間」欄位，所以頁面上只能寫「最後確認：YYYY-MM-DD」，語意要標明。

### 一個實測發現的坑

`md5()` 產生 32 字元字串，現值表因此膨脹到 **246 MB**，比主資料 Parquet 還大（2026-09-12 量測）。已改用 `hash()`（DuckDB 內建 64-bit 整數雜湊），同一天量到 current.parquet **120 MB**（省一半）；現值大小看 `status.mjs data` 的磁碟佔用。碰撞風險在千萬列的量級下約 10⁻⁵，而且碰撞的後果只是「漏偵測一次價格修正」，不是資料損毀——可以接受。**實作已採用 `hash()`，不要改回 `md5()`。**

## 4. Parquet 寫入：一天一檔，不要用 PARTITION_BY 增量

實測到的陷阱：

```sql
-- ✗ 錯的：每日增量這樣寫，整個 year=2026 分區會被清成只有當天
COPY (...一天的資料...) TO 'data/parquet/farm_trans'
  (FORMAT parquet, PARTITION_BY (year), OVERWRITE_OR_IGNORE);
-- 2026-09-12 實驗（重現：ingest/probe/duck-overwrite.mjs）：year=2026 從 714,855 筆變成 3,500 筆
```

```sql
-- ✓ 對的：直接指定檔名，一天一檔
COPY (...一天的資料...) TO 'data/parquet/farm_trans/year=2026/d-2026-09-08.parquet'
  (FORMAT parquet, COMPRESSION zstd);
-- 實測：同名再寫入是「覆蓋」→ 重抓同一天是冪等的，不會產生重複列
```

`PARTITION_BY` 只在第一次全史轉換時用（2026-09-12 量測：17.7 秒跑完當時的 5,362 天）。之後每日都是寫單檔。
讀取一律用 `read_parquet('data/parquet/farm_trans/**/*.parquet', hive_partitioning=true)`，`year` 會自動成為欄位，查單一年份時 DuckDB 只讀該分區。

小檔案數量：一年約 365 個檔、十年 3,650 個（現有檔數：`status.mjs data` 的「parquet 檔數」）。DuckDB 讀幾千個小檔沒問題，但若之後變慢，做法是**每年一次把當年合併成單檔**，不是改分區策略。

## 5. 型別：來源給什麼就存什麼，轉換留到聚合層

DuckDB 對原始 JSON 的 schema 推斷（實測穩定）：

```
交易日期 VARCHAR    "115.09.08"  民國年字串
種類代碼 VARCHAR    可為 NULL（筆數查 ingest/probe/farm-trans-stats.mjs 輸出的 nullType）
作物代號 VARCHAR    "LA1"、"rest"
市場代號 VARCHAR    "104"（要當字串，不能轉數字，否則 "0xx" 開頭會出事）
上/中/下/平均價 DOUBLE
交易量 DOUBLE
```

L1（`data/parquet/`）**保留原始欄名與型別**，只加一個 `year`（分區用）。民國年轉西元、`rest` 列的處理、單位換算都在聚合層做。理由與 seh.tw L1-FORMAT 相同：L1 只做「忠實搬運」，判斷留給後面，這樣改判斷不需要重抓。

## 6. 聚合層與頁面層

```
data/agg/
  plv3_day.parquet       作物(PLV3) × 市場 × 日   批發，交易量加權
  plv3_xun.parquet       作物 × 旬               批發／產地價對齊用（產地價主要是旬）
  plv3_month.parquet     作物 × 月               三層價差用（零售 CPI 是月）
  market_day.parquet     市場 × 日               市場頁、健康檢查
```

2026-09-12 量測（全量重算）。現況跑 `node scripts/status.mjs data` 的「聚合」段：

```
聚合來源      13,167,091 列 / 353 個 PLV3 作物 / 21 個市場代號
plv3_day       6,343,784 列   4.5 秒   72 MB
plv3_xun         923,272 列   1.7 秒    8 MB
plv3_month       385,543 列   1.6 秒    4 MB
market_day       146,180 列   1.6 秒    1.5 MB
整支跑完                      11.9 秒
```

README §6 原本預期這層需要增量更新。**全量重算只要十幾秒，所以增量先不做**——增量的錯誤（漏更新某個旬）比全量重算的成本難查得多。每年資料成長約 7%，等它超過 60 秒再改成增量（60 秒是設計判準；現在跑幾秒看 `status.mjs data` 的四表耗時），屆時的做法是只重算「近 N 天所屬的旬與月」加上當年的 `plv3_day`。

抽樣驗證（甘藍＝高麗菜的月加權均價，元/公斤。下面是 2026-09-12 當時的值；`aggregate` 每次跑完都會印同一組抽樣，要現值看 run log）：

```
2026-09  台北一 22.79  全國 26.95
2026-08  台北一 23.79  全國 27.42
2026-07  台北一 28.26  全國 28.81
```

數量級與現實相符（高麗菜批發價常年在 20–30 元/公斤）。`market_code = 'ALL'` 是跨市場加權，與各市場的列並存在同一張表，`plv3_xun` 與 `plv3_month` 都有。

### 完整性對帳（`check-coverage.mjs`）

L1 不會全部進到聚合層，這支把差額拆開，確認少掉的都是預期的。六列的意義固定，數字每天變——
跑 `node scripts/status.mjs data` 的「對帳」段，或直接 `cat data/coverage.meta.json`：

```
1 全部 L1                     ← 分母
2 rest 休市列                  交易量必為 0
3 交易量 <= 0（非 rest）         來源自己的錯誤，見下
4 身分表查不到（join 失敗）       ← 必須是 0
5 confidence < 0.8            進 review queue，不進聚合（見 §12）
6 進入聚合層
恆等式：2+3+5+6 = 全部 L1     ← `reconciled` 欄位就是在檢查這條
```

**被擋掉的列只佔很小的交易量比例**，而且集中在花卉品種細分（最大的一筆是火鶴花的品種細分，全在 review queue）。
擋掉的列數％與交易量％、以及逐年覆蓋率的範圍，都在 `status.mjs data` 的同一段；逐年逐一的值用
`jq .byYear data/coverage.meta.json`。要看的是「有沒有哪一年突然掉下來」（那會代表該年有新代碼沒對應），不是絕對值。

**來源有負的交易量**：全史有幾列負值（2026-09-12 查到 6 列、合計 −243 公斤、最負 −130，例如 `107.12.29` 的 `SD9`）。
聚合層用 `交易量 > 0` 擋掉，但這是農糧署資料本身的錯誤。現況查法：用 `transform/_db.mjs` 的 `readL1()` 跑
`SELECT count(*) AS n, sum("交易量") AS total, min("交易量") AS worst FROM <L1> WHERE "交易量" < 0`。

### 頁面層（`emit-page.mjs`）

頁數（作物／市場／作物 × 市場）、per-page JSON 檔數、可收錄頁數與比例：`node scripts/status.mjs page`。
沒過門檻的頁照常存在且可連，只是帶 noindex。

作物 × 市場的組合數遠少於 README §6 估的 6,000，因為只產生實際有交易的組合。收錄門檻：近 90 天有 30 個交易日且交易量 ≥ 10,000 公斤；退出門檻 15 天 / 3,000（進出門檻不同以避免 sitemap 抖動，遲滯判斷要接 `page-state.ndjson` 的歷史，尚未實作）。

`data/page/crop/*.json` 目前把各市場的近 90 天日序列都塞在同一檔，與 `crop-market/*.json` 有重複，`data/page/` 有一半的體積是這個（磁碟佔用看 `status.mjs data`）。等頁面模板定了再決定要不要瘦身——先確保資料齊全，不要提前優化。

頁面層每頁一個 JSON，Astro build 只做讀檔：

```
data/page/crop/LA1.json            品項頁（含 14 年月均價序列、跨年同期比較）
data/page/market/109.json          市場頁
data/page/crop-market/LA1-109.json 品項 × 市場（只產生有交易的組合）
data/page/cheap-this-week.json     「本週便宜」
```

`slug` 與收錄門檻沿用 seh.tw §6 的三條原則：**網址永久**（slug 寫進 `data/slug-registry.ndjson`，append-only）、**收錄與否每天重算**、**進出門檻不同以避免抖動**。門檻用「近 90 天交易日數」與「交易量」，把雜訊組合擋掉（2026-09-12 查到的例子：N05 在屏東市 14 年只有 2 天交易）。

## 7. 版控與備份

| 路徑 | 進版控？ | 理由 |
|---|---|---|
| `ingest/sources/`、`transform/`、`overrides/` | 是 | 程式與人工判斷 |
| `ingest/raw/` | **否** | 好幾百 MB 且逐日累積，git 放不下 |
| `data/parquet/`、`data/agg/` | **否** | 二進位、可從 raw 重建（2026-09-12 量測 17.7 秒） |
| `data/observation/` | 否（但要備份） | 唯一無法從 raw 重建的東西（見下） |
| `data/page/` | 否 | 可重建 |
| `ingest/state.json` | 否 | 主機本地狀態 |

**`data/observation/` 是唯一不可重建的資料。** raw 只保留「每次抓到的內容」，但「某筆在哪一天被改過」這件事一旦沒記錄就永久失去。備份優先序：`observation/` > `raw/farm-trans/` > 其他。

**已經是 git repo**（`origin` = <https://github.com/LightChang/hokhong.tw>），`.gitignore` 已排除上表中「否」的路徑——raw 有好幾百 MB，進了 git 就很難拿掉。不進版控的資料改走 GitHub release 的 `data-history` 與 `data-current` 兩個 tag（機制見 `ingest/SCHEDULE.md`，各資產現值大小 `node scripts/status.mjs release`）。

## 8. 每日流程

主機上只有兩個入口，都可以重複執行（冪等）：

```
02:00  node ingest/run.mjs        取得層：依各來源頻次判斷到期
03:30  node transform/run.mjs     轉換層：各步依序（步名與順序：status.mjs steps）
```

每日實際跑幾秒、每一步印出什麼，看那次 Actions run 的 log——`node scripts/status.mjs online`
會印出最近幾次的 run id 與對應的 `gh run view <id> --log`，那份輸出才是線上現況的權威來源。

2026-09-12 在本機量到的各步耗時（每日模式）。留著是為了說明「哪一步最貴」，不是現況：

```
to-parquet       1.0s   只轉近 7 天，已存在且沒更新的略過
observe          5.1s   比對近 7 天
identify         1.1s   代碼 → 自動採用（含交易量佔比）
check-coverage   2.3s   對帳與逐年覆蓋率
aggregate       11.1s   全量重算四張聚合表
emit-page        4.6s   寫出每頁一個 JSON
```

任一步失敗就停、回非零，並提示 `--from <步驟>` 續跑（前面的產物沿用）。順序相依由這支保證——最怕的情況是「頁面用了舊的身分表」，那不會報錯，只會靜靜產出錯的聚合值。

每層都會寫一個 meta 檔，出問題時先看它們（都有 `builtAt` / `ranAt`）：

```
data/parquet/farm_trans.meta.json   L1 列數、交易日數、空檔日、逐年列數
data/observation/observe.meta.json  未變／修正／新增筆數
data/identity/identity.meta.json    各規則命中數、種類洩漏檢查、review queue 筆數
data/coverage.meta.json             完整性對帳是否通過、逐年覆蓋率
data/agg/agg.meta.json              四張表的列數與耗時
```

首次上主機的順序：`pnpm install --frozen-lockfile` → `node ingest/sources/farm-trans.mjs`（全史回補，2026-09-12 實跑約 4–5 小時，一天一個請求）→ `node transform/run.mjs --full` → 之後交給 cron。

## 9. 站台層（Astro）

### 服務對象是「買菜的人」，不是資料的讀者

第一版做錯了：首頁的 KPI 是「收錄品項 N、市場 N、比較組合 N」（2026-09-12 的值是 173／35／3,049）——那是資料集在自我介紹。
買菜的人不關心收錄幾個品項，他要知道的是**今天該不該買**。而 README §5 列的第 5 個缺口正是
「沒有『現在什麼便宜』的入口，全部都要先知道品名再查」，第一版卻仍然是「先知道品名再查」的結構。

改版後首頁只回答一件事：這週什麼划算、什麼先別買。**一頁寬、一頁高，不捲動**，所以沒有圖表、
沒有長清單、沒有資料集介紹。

### 主數字是漲跌幅，不是價格

我們有的是批發價，買菜的人面對的是零售價。台中公有零售市場對照批發的倍數逐品項差很多——
現況的範圍與中位數跑 `node scripts/status.mjs page` 的「零售實測」那一行。2026-09-13 量到的樣貌：

```
零售 ÷ 批發 中位數 2.0 倍，但範圍 1.00–4.01
  空心菜 1.01（幾乎不加價）   高麗菜 2.97   大白菜 3.11
```

用單一倍數推估攤價一定會錯，錯了這站就不值得看。而「比常年便宜 38%」在批發與零售之間方向一致，
可以傳遞。所以主數字是漲跌幅；只有對得上台中實測的品項才顯示實際攤價（幾個：同一支指令），其餘只給批發價，不推估。

### 人工資產（`overrides/`）

| 檔案 | 內容 | 怎麼來的 |
|---|---|---|
| `overrides/crop-common-name.json` | 官方名 → 俗名（甘藍→高麗菜） | 逐項核對各作物底下**實際的批發品名**，不是憑印象 |
| `overrides/crop-retail-map.json` | 台中零售各欄 → 站上作物 | 魚肉蛋欄一律標 null；多欄對同一作物時把訪價合起來算中位數（見 §14）。欄數與對映以該檔 `columns` 為準 |
| `overrides/crop-origin-name-map.json` | 產地價品名 → 官方名 | 先查這張表，查不到才走官方 SAP 對應 |
| `overrides/season-name-map.json` | 盛產表作物名 → 官方名 | 2026-09-26 實查 89 個盛產名：45 個字串相等、31 個是別名、13 個我們沒有（雜糧與茶類）。不補這張表，當季會少掉一半品項 |
| `overrides/market-geo.json` | 市場座標與全名 | OSM Nominatim ＋縣市驗證；查不到座標的以該檔為準 |
| `overrides/festivals.json` | 除夕／初一／端午／中秋／清明的國曆日期 | 香港天文台逐年對照表，人事行政總處辦公日曆交叉核對。**不要用 Node 內建的 Intl 農曆**：2027 初一它算成 2/7，朔實際落在 2/6 23:56（台北） |

單位這件事沒有人工表也不行：**產地價來源沒有單位欄**，只能從「產地價格月平均」的作物名
尾綴推（177 個品名元/公斤，花卉元/支、檳榔元/粒、滿天星元/把、蝴蝶蘭元/吋盆）。
非元/公斤的品名一律不進價格鏈，否則會跟批發的元/公斤相除算出無意義的倍率。

核對時（2026-09-12）修正的錯誤假設：**枸櫞其實是檸檬**（底下 100% 是雜柑-檸檬）、**韭蔥其實是蒜苗**、
**隼人瓜 65% 是瓜苗也就是龍鬚菜**、**甜橙 80% 是柳丁**、**青花菜是綠花椰而花椰菜是白花椰**。
萵苣底下混了油麥菜（大陸妹）、本島圓葉（A 菜）、結球萵，無法用單一俗名代表，所以並列。

### 替代品建議：使用者價值優先於版面多樣性

貴的品項給一個同類替代（同官方中類 PLV2、同期有量、自己沒漲超過 20%）。
`plv3_key` 的第 4–5 碼就是 PLV2，不必改 identify 就拿得到分類。

曾經加過「已推薦過的降權」來避免六個貴品項有四個都建議芹菜，結果是把最划算的讓給排前面的品項，
後面的只能拿到「改買韭菜 +13%」這種還在漲的替代品。**已改回只給 1 個最佳替代、不去重**——
同一個高麗菜被推薦三次沒關係，那本來就是現在最划算的葉菜。

品項頁的替代建議**只在該品項漲超過 20% 時才顯示**。實測踩到：高麗菜明明「便宜 25%」，
頁面卻還掛著「太貴的話 → 改買芹菜」，很荒謬。資料層照算不誤，要不要顯示是頁面層的判斷。

```
src/
  layouts/Base.astro           頁首頁尾、meta、noindex、字型
  components/PriceLine.astro   SVG 折線圖（無外部圖表 library）
  lib/pagedata.mjs             讀 data/page/*.json 與顯示格式
  pages/                       index / cheap / about / crop / market / crop-market
  styles/tokens.css            設計系統副本，禁止編輯（pnpm run sync:tokens 同步）
  styles/site.css              站台樣式，只用 token，不得寫死顏色或低於 18px 字級
public/favicon.svg
```

`pnpm build` 產出幾頁、sitemap 收幾個網址：`node scripts/status.mjs page`（本機的 `page-state.ndjson`）與 `node scripts/status.mjs online`（線上 sitemap）；`dist/` 未壓縮多大自己 build 完 `du -sh dist`。sitemap 只收品質達標的頁加上幾個靜態頁，沒過門檻的照常存在且可連，但帶 `noindex`——收錄與否由 `data/page/page-state.ndjson` 決定，`astro.config.mjs` 只是把那個判斷接上 sitemap，不重新發明門檻。

### 全站一個螢幕寬、一個螢幕高

每一頁都塞進一個 viewport，外層永不捲動（`.screen` 用 `height: 100dvh` + `overflow: hidden`）。
內容多的頁面靠**分頁切換**，不是往下堆：

| 頁型 | 分頁 |
|---|---|
| 品項頁 | 14 年走勢 / 跟往年比 / 近 90 天 / 各地價差 / 為什麼貴（颱風、量價關係、年節往例、價格鏈，有哪幾段看該作物有沒有資料） |
| 市場頁 | 現在最便宜 / 現在最貴 / 到貨量 / 休市日 |
| 颱風與菜價 | 還沒回穩 / 已經回穩 / 颱風前先買什麼 / 歷次颱風 |
| 完整榜單 | 蔬果變便宜 / 蔬果變貴 / 花卉 |
| 品項清單、市場清單 | 蔬菜 / 水果 / 花卉 |
| 關於資料 | 五段說明各一頁 |

分頁數上限是 5（CSS 逐一配對），所以品項頁把「為什麼是這個價」的四件事收在同一個
面板裡分段，而不是各開一個分頁。

分頁是**純 CSS**（`radio` + `:checked` + `~` 選擇器），靜態站不需要 JS。分頁數上限 5，
CSS 用 `:nth-of-type` 逐一配對 input 與 panel。

長列表（品項清單、40 名榜單）讓**面板自己內捲**，外層仍是一個螢幕——這是刻意的取捨：
清單本來就該能捲，但整頁不該長到四個螢幕。2026-09-13 量測：品項頁改版前 3,993px（4.4 個螢幕），改版後 900px。

`100dvh` 不是 `100vh`：手機瀏覽器的網址列會吃掉 vh，用 dvh 才是實際可視高度。

### 圖表的色彩為什麼只用兩色

`design-tokens` 的語意色扣掉狀態保留色（critical/warn/pass/info 不得挪用為序列）後只剩 5 個。這 5 色在 2026-09-12 用 dataviz 的 validator 量過（surface `#f5f6f8`）**不合格**：

```
purple #7830b8 ↔ link #1e5ab8   deutan ΔE 0.1   正常視覺 ΔE 14.2（低於 15 硬底線）
cyan   #1e7a8a                  chroma 0.085（低於下限，會讀成灰）
```

通過的組合只有 **link 藍 `#1e5ab8` + pink 粉 `#b8306a`**（CVD ΔE 13.1、正常視覺 26.4、對比皆 ≥ 3:1）。所以多序列一律走 **emphasis**：主角一色、比較對象一色、其餘 `--text-muted` 灰。想加第三條有顏色的線就得動用狀態色，那會讓「紅色」同時代表「嚴重」和「某個市場」——寧可不加。

其他遵循的圖表規則：單一 y 軸（絕不雙軸）、線 2px、格線與軸為 hairline 實線（不用虛線）、只在端點做選擇性標註、每張圖都有 `<details>` 表格檢視（值不只存在 tooltip 裡）、hover crosshair 為加分而非唯一途徑。

### 首頁為什麼把花卉分流

實際截圖檢查（2026-09-13；這步不能省，兩個問題都是看了才發現的）：

1. 「比常年便宜」前十名有七個是花卉（當時是小菊、一枝黃花、雞冠花、非洲菊、大菊、千代蘭…；榜單成員每天換）。花卉的價格波動本來就比蔬果劇烈，混在一起排名會把主線稀釋掉——站台要回答的是「今天什麼菜便宜」。改成首頁蔬果榜與花卉榜分開，完整的混合排名留在 `/cheap`。
2. 市場清單第三欄「近 90 天有交易」被折成兩行，斷字成「天有／交易」。`.rows` 第三欄只有 7rem 且 `.num` 沒有 `nowrap`。已加寬到 9rem 並加上 `white-space: nowrap`，文案同時縮短為「近 90 天」。

修正後用 computed style 複驗（2026-09-13）：100 個數值欄高度全為 32px（單行）、0 個折行、無水平溢出、蔬果榜前 16 列不含花卉。

## 10. 產地→批發→零售：為什麼多數品項不能比

README §5 的缺口 4 是「沒有產地→批發→零售的縱向對照」。資料都有（產地價幾十萬筆、細到鄉鎮；
列數與品名／縣市數看 `status.mjs data` 的「產地價」那一行），但實測發現**多數品項的產地價與批發價不可直接相除**。

先把兩邊拉到同一旬排除時間錯位，可比品項裡仍有相當多是批發低於產地。以下是 **2026-09-13 的一次性分析
（基準旬 2026-08 下旬，腳本沒留下來）**：當時 65 個可比品項中有 21 個批發低於產地——

```
蓮子(脫殼)  產地 716.0  批發  41.5   ×0.06   產地查脫殼蓮子，批發是帶殼
文旦        產地  99.0  批發  21.0   ×0.21   產地查精選果，批發含所有等級
綠竹筍      產地  91.9  批發  55.2   ×0.60
甘藷        產地  27.8  批發  17.0   ×0.61
番茄(黑柿)  產地  84.1  批發  66.0   ×0.79   產地按品種分別查報，批發是全品種加權
```

當時倍數中位數只有 1.20，遠低於合理的產地→批發價差。原因不是時間錯位，是**兩邊查的根本不是同一個東西**：
產地價是特定品種／等級的查報價，批發價是該作物所有品種的交易量加權。

### 判準：對不齊就不顯示

跟「零售價不推估」同一個原則。自動判準，不逐筆人工：

| 條件 | 理由 |
|---|---|
| 產地與批發取**同一旬** | 產地價比批發晚約一個月，基準旬以產地為準 |
| 批發 ÷ 產地 落在 **1.0–4.0** | 低於 1 是品項不對等（文旦、蓮子）；高於 4 是花卉查報單位不同（2026-09-13 當時：劍蘭 ×19.7、大菊 ×12.1） |
| 同一作物只能有**一個**產地品名對應 | 番茄同時有「黑柿」與「牛蕃茄」兩筆查報，無法判斷哪個代表該作物 |

通過的品項才顯示價格鏈，其餘連提都不提。現況跑 `node scripts/status.mjs page` 的「價格鏈」段：
可比幾個、其中三層俱全（含台中零售實測）幾個，以及被擋下的各個理由各幾個（`wholesale-below-origin`、
`ambiguous-origin-item`…）。逐筆的值在 `data/page/crop/*.json` 的 `chain` 欄位
（`comparable` / `xun` / `origin` / `wholesale` / `retailPerKg` / `originToWholesale` /
`wholesaleToRetail` / `farmerShare`）。

被擋掉的一對多很能說明問題：**青江菜**同時對到「青江白菜」與「小白菜」、**蓮**對到「蓮子(脫殼)」
與「蓮藕」、**梨**對到「甘露梨／新興梨／新世紀梨」——這些都無法判斷哪一筆代表該作物的行情。

通過判準的長這樣（2026-09-13 當時的值，元/公斤，農民佔＝產地 ÷ 零售；現況逐筆看上面那個 `chain` 欄位）：

| 品項 | 產地 | 批發 | 零售 | 產→批 | 批→零 | 農民佔 |
|---|---|---|---|---|---|---|
| 番石榴 | 63.4 | 69.7 | 75.0 | ×1.10 | ×1.08 | 85% |
| 香蕉 | 27.5 | 29.0 | 55.0 | ×1.05 | ×1.90 | 50% |
| 空心菜 | 33.8 | 47.2 | 75.0 | ×1.40 | ×1.59 | 45% |
| 高麗菜 | 24.3 | 27.3 | 80.0 | ×1.12 | ×2.93 | 30% |
| 洋蔥 | 15.0 | 25.2 | 53.3 | ×1.68 | ×2.12 | 28% |
| 柿子 | 25.0 | 58.8 | 183.3 | ×2.35 | ×3.12 | 14% |

番石榴 85% 是因為產地直銷比例高、價差小；柿子只有 14%，落差集中在零售端。
這兩個極端正好說明為什麼不能用單一倍數推估——也是本站不推估攤價的理由。

## 11. 颱風標註與對比

README §5 的缺口 3。氣象署颱風資料庫的警報列表已抓（`cwa-typhoon-warnings`），涵蓋 2012 年之後；
有幾次紀錄、幾個作物算得出回穩天數、最近一次距今幾天，跑 `node scripts/status.mjs page` 的「颱風」那一行。
`transform/typhoon.mjs` 把它跟批發日價對起來，回答兩件事：**現在貴是不是因為颱風**、**還要多久回穩**。

### 「回穩」怎麼定義，以及兩個踩過的坑

```
基準     颱風警報結束前 14 天的全國加權均價（至少要有 5 天資料）
高峰     結束後 30 天內的最高價
回穩     從「高峰之後」往後找，第一天回到基準 × 1.1 以內
有影響   高峰比基準貴兩成以上，才算這次颱風真的影響了這個作物
```

第一版寫成「從颱風結束當天開始找第一個低於基準 ×1.1 的日子」，跑出來是
**「油菜漲 128% 但 2 天回穩」**（2026-09-12 當時的值）——颱風後漲勢通常延後幾天才到頂，所以在漲上去之前就誤判回穩了。
改成從高峰之後才算。

第二個坑：把每一次颱風都算進中位數，包含那些根本沒讓價格動的，中位數又被拉回 1–2 天。
改成只統計「有影響」的那幾次。

## 12. 那些對不上作物身分的，決定不處理

`data/identity/review-queue.ndjson` 裡的代碼沒有作物身分。**決定維持現狀**，理由是它們大多不是
「人工判斷就能解決」的。筆數與交易量佔比跑 `node scripts/status.mjs data` 的「作物身分」段
（`unmapped` 與 `no-source-name` 兩條規則就是下面兩類），分類方式與理由是：

| 類型 | review queue 的 `kind` | 為什麼 |
|---|---|---|
| 官方名冊查無此作物 | `crop-unmapped` | 火鶴花、茉莉花、石斛蘭…**官方統一代碼表裡就沒有這些花**，硬填等於自己發明分類 |
| 來源沒給名稱 | `crop-no-source-name` | `OA`、`FJ4` 只有代碼，名稱空白，無從判斷 |

另外有一個獨立指標：`data/identity/identity.meta.json` 的 `officialCategoryMismatch`
（香茅、棉花這種「官方歸特用作物類、與交易站的種類代碼對不上」的情況）。它的定義與上表兩類不同——
那些代碼仍然有身分，只是分類對不上，所以不會出現在 review queue 的計數裡。以那個欄位為準，
不要拿它跟上表相加。

這批合計只佔全站交易量約 1%，而且幾乎全是花卉（按 review queue 的 `payload.tc_type` 分組，絕大多數是 N06）。
花卉之外的覆蓋率高到對「買菜的人」這個定位沒有影響——依種類的交易量覆蓋率可以用 §6 的對帳查法
加 `GROUP BY "種類代碼"` 自己算。

若日後要讓這些花卉也能成頁，做法是替它們自建站內分類（不掛官方代碼），但頁面必須標明那是站內自訂、
不是官方權威。這是刻意沒做的事，不是遺漏。

## 13. 這個決定放棄了什麼

- **線上即時查詢。** 所有頁面在 build 時決定。要做「使用者自訂區間比價」就得另外開 API，那時才需要真正的資料庫。
- **build 期間多一個依賴。** `@duckdb/node-api`（實際拉幾個套件：`pnpm ls --depth 1 @duckdb/node-api`）。取得層仍然是零依賴的原生 fetch，所以每日抓資料不受影響。
- **`data/parquet/` 不進版控**，所以沒有 seh.tw 那種「git diff 看今天資料變什麼」的便利。替代品是 `observation/history/`，它記的是同一件事，但要寫查詢才看得到。

## 14. 買菜清單：只存在瀏覽器

首頁第二個分頁「我的買菜清單」讓使用者自己挑常買的菜，看它們現在貴不貴。**沒有後端、沒有登入、沒有帳號**，
清單存在 `localStorage` 的 `hk.list`（一個 slug 陣列），站台仍然是純靜態。

- **資料來源**：`transform/emit-page.mjs` 產出 `data/page/list-source.json`（排除花卉 N06；品項數與檔案大小看
  `status.mjs page` 的「買菜清單／品項搜尋來源」），
  每項含 `slug / name / changePct / wholesale / retailPerCatty / seasonal / alt`。首頁把整包內嵌進 HTML，
  瀏覽器端不再發第二次請求。
- **預設清單**：`listSource.defaults` 是一份家常菜清單（高麗菜、青江菜、空心菜…；幾樣看 `status.mjs page`），**只在第一次造訪時寫入**。
  `window.hk.read()` 回 `null` 代表「還沒初始化」，回 `[]` 代表「使用者自己清空」——兩者要分得開，
  否則清空後預設值會一直跑回來。
- **helper**：`src/layouts/Base.astro` 的 `window.hk`（read/write/has/add/remove/toggle），
  寫入後發 `hk:list` CustomEvent，首頁清單與品項頁的「加入買菜清單」按鈕都靠這個事件同步。
- **排序**：貴的排最前面。清單的用途是「今天別買什麼」，不是字典。

### 零售價的來源與極限（2026-09-13 查證）

零售價只有一個來源：臺中市公有零售市場每日蔬果價格表（經發局，data.gov.tw/dataset/84539，
政府資料開放授權第 1 版），公有市場每日訪價，元/台斤，`0` = 當日未訪到。
取**近 30 個訪價日的中位數**（不是最新一天，避免單日跳動）。來源端只保留近一年，
所以要每日累積，漏抓就永久缺。幾個市場、檔案裡含幾個訪價日，以最新那個檔為準：讀
`ingest/raw/taichung-retail/` 排序最後一個 `.json.gz`，數 `市場名稱` 與 `訪價日期` 的 distinct 值。

**全台只有臺中開放這種資料。** 查證過：政府資料開放平臺、新北（查無）、高雄（只有市場名冊，
無價格）、桃園（`每日大宗蔬果行情價格表` 是批發，且已下架）、臺北（市場處無此資料集）、
新竹（農產運銷公司是批發）。農業部開放平臺只有批發交易行情，沒有零售資料集。
所以「多接幾個縣市」目前無路可走，不是沒做，是不存在。

原始表的欄位分兩種：蔬果欄與魚肉蛋欄（後者不在批發行情裡，無處可對，一律標 null）。
蔬果欄去重後的作物全部都上站了——幾欄、對到幾個作物看 `overrides/crop-retail-map.json` 的 `columns`；
站上有幾個品項、其中幾項有零售價看 `status.mjs page`。其餘只顯示批發價，不推估攤價。

`棗子` 欄有資料（2026-09-13 量到近 30 訪價日 118 筆、中位數 78 元/斤）但仍留空：官方名冊只有
「印度棗／中國棗」，批發行情資料裡沒有對應品項，掛不上去。這是資料結構的限制，不是漏標。

**多欄合併（2026-09-13 改）**：蔬果欄裡有幾個作物對到多欄（寬皮柑、鳳梨、梨、柿各三到四欄，
胡瓜／紅龍果／檬果／小果番茄各兩欄；哪一個對到幾欄以 `overrides/crop-retail-map.json` 的 `columns` 為準）。
原本只取「有值比例最高的那一欄」，等於用單一品種的牌價代表整個品類，而且白丟樣本。
改成把同作物的所有欄合起來算中位數後（下表是 2026-09-13 改版前→改版後的值）：

| 作物 | 樣本 | 中位數（元/台斤） |
|---|---|---|
| 寬皮柑 | 173 → 320 | 70 → 48（原本被茂谷柑主導） |
| 鳳梨 | 146 → 366 | 37 → 30 |
| 小果番茄 | 176 → 265 | 130 → 110（原本被玉女主導） |
| 柿 | 104 → 145 | 110 → 100 |
| 檬果 | 201 → 261 | 83 → 80 |
| 胡瓜 | 330 → 599 | 45 → 44 |
| 梨 | 116 → 226 | 70（不變） |
| 紅龍果 | 242 → 388 | 63（不變） |

品種之間確實有價差，但中位數本來就是回答「這類東西在市場上大概多少錢」，不是某一品種的牌價。

**同名多實體的掛載錯誤（2026-09-13 修）**：零售價與產地價的 key 都是官方名（PLV3），但一個官方名
會對到多個作物實體。「紅龍果」有三筆——N06 花卉一筆、N05 兩筆（其中一筆近 90 天只交易 6 天、
批發 5 元）——三筆全被掛上同一個零售價 105 元/公斤，於是算出「零售是批發的 0.59 倍」與「21 倍」（都是 2026-09-13 當時的值）。
`桃`、`蓮`、`南瓜`、`黃秋葵` 的花卉筆也同樣拿到蔬果的產地價去組價格鏈。

修法：組完 `crops` 後先決定每個官方名的**代表實體**（排除 N06、取近 90 天交易日最多的那一筆），
零售價與產地價只掛給代表。順帶修掉「當季」標記漏到花卉（百合、蝴蝶蘭曾被標成當季）。

修正後（2026-09-13 當時）：有零售價的品項 30 → 28（先前是重複虛胖）、價格鏈可比較 30 → 29、
零售 ÷ 批發倍率範圍從 0.59–21.00 收斂成 1.00–4.01、被標當季的花卉 3 → 0。
這幾個數字的現值跑 `node scripts/status.mjs page`。

**訪價密度會影響顯示**：葉菜幾乎天天訪得到價，當季水果只有產季那幾週（2026-09-13 的例子：絲瓜 cover 1.00／386 筆、
柿子 cover 0.13／145 筆；逐筆現值在 `data/page/crop/*.json` 的 `retail.cover` 與 `retail.samples`）。
cover < 0.35 的品項，KPI 改標「僅產季訪得到價，N 筆」，
價格鏈則**不換算農民拿幾成**——那個數字會被當全年結論讀，但它的零售端只來自產季。
### 圖表的配色與互動（2026-09-13）

**漲跌幅色階是 diverging，不是 sequential。** 便宜↔貴有極性，所以規範要求兩個色相 + 中性灰中點、
每臂等距，而不是單色相由淺到深。兩臂深端刻意等於既有語意色（綠 `--color-pass`、紅 `--color-critical`），
往中點方向各推兩階：

| 級距 | 便宜臂 | 貴臂 |
|---|---|---|
| 近中點 | `#69a275` L0.66 | `#e08f88` L0.73 |
| 中階 | `#318c4c` L0.57 | `#dc5e59` L0.64 |
| 深端 | `#007424` L0.48 | `#d40924` L0.55 |

兩臂各自以 `validate_palette.js --ordinal` 驗過（2026-09-13：單調 L、相鄰 ΔL ≥ 0.06、單一色相、
淺端對 `#ecedf0` 對比 2.55:1 與 2.12:1，皆過 2.0 門檻）。diverging/ordinal **不能**跑類別色的六項檢查，
那會 by design 失敗。

**色階只用在色塊，不染文字**：淺端 2.1–2.6:1 遠低於文字需要的 4.5:1（WCAG 門檻）。
漲跌數字仍用 `.up`/`.down` 的原始語意色（2026-09-13 量到 5.09:1 / 4.64:1，合格）。

**各地價差不套色階。** 市場是 nominal（換順序不改變意義），規範明文禁止用顏色重複編碼長度已經
表達的數值；那裡只保留「最便宜／最貴」兩個狀態色。

**色塊只放在「沒有按漲跌排序」的清單。** 首頁的「這些划算／這些先別買」與 `/cheap` 榜單本來就
依漲跌排序、文字也已上紅綠，再加色塊等於第三次編碼同一件事——規範反對用識別通道重複已表達的量，
所以這兩處撤掉。留著色塊的是級距真正混雜的地方：`/crop` 全品項（按名稱排序，漲跌在 +87、+11、
−32、+82 之間跳）、市場頁的品項清單、以及首頁的買菜清單。

**手機不顯示色塊。** 數值欄在 390px 寬只有 96px，「便宜 33%」加上色塊 2026-09-13 量到 108px 會溢出；
方向本來就由紅綠文字表達，所以 ≤760px 把 `.rows .num .lv` 收起來（元素仍在 DOM，只是不顯示）。
色塊一律 `aria-hidden="true"`＋`title`：旁邊的文字已經把意思講完，讓螢幕閱讀器再唸一次是重複。

**互動**：折線是 crosshair + 單一 tooltip 列出所有序列；長條改成**每條自己是 hit target**
（bars 不用 crosshair），hover 與鍵盤 focus 給相同內容，該條底色微亮作為回饋。
tooltip 內的品項名與市場名都是資料，一律用 `textContent` 寫入，不做字串拼 HTML。

**沒有引入 d3。** 座標與比例本來就已在 build 時算好，d3 的 scale/shape 幫不上；
站台是幾千頁純靜態（頁數：`status.mjs page`），每頁多載一份 d3 約 90 KB 換不到對應價值。動態需求（hover 回饋、
過場）用 CSS transition 與原生事件即可，且 `prefers-reduced-motion` 已在站上處理。

### `/crop` 的品項搜尋（2026-09-13）

品項分成蔬菜／水果／花卉三個分頁（幾個品項：`status.mjs page`），用眼睛找太慢。搜尋框跨三個分類一起比對，
**俗名和行情站官方名都比對**——使用者可能記得「高麗菜」，也可能記得「甘藍」；
站上有一批品項的俗名與官方名不同（空心菜↔蕹菜、檸檬↔枸櫞、蒜苗↔韭蔥、小黃瓜↔胡瓜…；
幾個看 `status.mjs page` 的「俗名與官方名不同」）。

- 搜尋結果與分類分頁**互斥顯示**，兩者共用 `.screen` 的同一個 `1fr` 列（`grid-row: 3`）。
  一開始讓兩者各佔一列，grid 會多長一列出來，把一頁高的版面撐破；
  查無時若兩者同時顯示，又會疊在同一格——所以查無改成隱藏結果區、提示話走搜尋列旁的 count。
- **重複名排序**：一個名字可能對到多筆（2026-09-13 的例子：「紅龍果」有水果兩筆、花卉一筆，其中一筆近 90 天只交易 6 天）。
  不刪資料（花卉的紅龍果是另一種東西），但排序讓交易正常的蔬果在前、花卉次之、交易量少的殿後，
  每列並標明「水果／花卉／交易量少」。

- **加一項的選單**：上百個 option 直接列出來太長，所以搜尋框（比對品名）＋分組選單兩手併用。
  分組不用官方中類（PLV2）原名——「漿果類」「仁果類」「鱗莖類」不是買菜的人腦中的分類——
  在 `emit-page.mjs` 的 `CAT` 表併成葉菜／瓜類／根莖／菇類／蔥蒜／茄果椒／豆類／花椰菜／芽菜／柑橘／水果／其他蔬菜，
  陣列順序就是選單的分組順序（組數與順序一律以該表為準），最後兩條規則通吃 N05／N04，不會有品項落不到分類。
- **版面**：桌機 `column-count: 2`，16 項一個螢幕看完不捲動；手機單欄、面板內捲動。
